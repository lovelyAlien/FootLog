# FootLog 제품 요구사항 문서 (PRD)

- 작성일: 2026-08-13
- 상태: 승인된 제품 기준
- 주요 독자: 프로젝트 소유자, AI 개발 에이전트
- 적용 범위: 공개 MVP

## 1. 문서 개요

이 문서는 FootLog의 제품 목적, 사용자 가치, 공개 MVP 범위, 단계별 우선순위와 객관적인 완료 조건을 정의하는 단일 제품 기준이다. 팀원과 AI 개발 에이전트가 같은 방향으로 판단하여 해석 차이에서 발생하는 재작업과 소통 비용을 최소화하는 것이 목적이다.

제품 요구사항이나 범위를 변경하려면 이 문서를 먼저 갱신한다. 구현 세부사항은 별도 설계 문서에서 정하되 제품 요구사항을 약화하거나 우회할 수 없다.

### 문서 우선순위

문서가 충돌할 때 다음 순서를 적용한다.

1. 이 PRD: 제품 목적, 사용자 가치, MVP 범위, 우선순위, 수용 기준
2. 최신 핵심 UX 설계: 상세 사용자 흐름과 인터랙션
3. 기반 설계: 아키텍처 원칙과 기술 방향
4. 구현 계획: 작업 순서와 구체적인 구현 방법

## 2. 제품 요약

FootLog는 사용자가 매시간 자신의 위치를 의식적으로 체크인하고, 일일 지도와 주간 비교를 통해 이동 패턴과 생활 반경을 공간적으로 돌아보는 개인 기록 앱이다.

제품의 핵심은 자동 이동 추적이 아니라 사용자가 현재 위치를 확인하고 직접 남기는 기록이다. FootLog는 반복되는 생활을 평가하거나 새로운 장소 방문을 과제로 제시하지 않는다. 객관적인 기록과 선택적인 회고 질문을 제공하여 사용자가 자신의 패턴을 스스로 발견하도록 돕는다.

## 3. 문제 정의와 사용자 요구

일반적인 위치 기록 서비스는 지속적인 백그라운드 추적이나 장소 소비 기록에 집중한다. 이는 사생활 침해에 대한 부담을 만들고, 사용자가 이동을 의식적으로 돌아보는 행위를 약화할 수 있다. 반대로 텍스트 중심 일기는 하루의 공간적 흐름과 생활 반경 변화를 직관적으로 보여주기 어렵다.

대상 사용자는 다음을 원한다.

- 자동 추적 없이 자신의 의지로 위치를 기록한다.
- 네트워크나 서버 상태와 무관하게 기록을 남기고 다시 본다.
- 하루의 이동을 지도와 시간 순서로 돌아본다.
- 기록이 쌓이면 반복 영역과 새로운 영역, 생활 반경 변화를 객관적으로 확인한다.
- 점수, 스트릭, 평가나 죄책감 없이 기록과 회고를 지속한다.

## 4. 제품 비전과 원칙

### 제품 비전

사용자가 자동 위치 추적 없이 의식적으로 남긴 기록을 통해 일상 이동과 생활 반경을 돌아보게 한다.

### 제품 원칙

1. **사용자 확정**: 사용자가 현재 위치를 확인하고 명시적으로 확정하기 전에는 체크인을 저장하지 않는다.
2. **로컬 우선**: 체크인과 회고 데이터는 기기에 먼저 저장하며, 핵심 기록과 조회는 오프라인에서도 동작한다.
3. **프라이버시 우선**: 백그라운드 위치를 수집하지 않고 `사용 중` 위치 권한만 요청한다.
4. **회고 중심**: 기록 자체보다 하루와 한 주의 이동을 돌아보는 경험을 제품의 중심에 둔다.
5. **비평가적 표현**: 점수, 순위, 스트릭, 성취 배지와 죄책감을 유발하는 표현을 사용하지 않는다.
6. **객관적 발견**: 제품은 탐험을 명령하거나 회고 내용을 자동 평가하지 않고 관찰 가능한 이동 사실만 제공한다.
7. **실패 격리**: 사진이나 서버 동기화 실패가 체크인과 다른 로컬 기록을 막거나 손상하지 않게 한다.

## 5. 대상 사용자

### 핵심 사용자

일상 이동을 자동 추적당하지 않으면서 의식적으로 기록하고, 자신의 생활 반경을 돌아보고 싶은 개인 사용자.

### 핵심 사용 상황

- 정시 알림을 받고 현재 위치를 확인하여 빠르게 체크인한다.
- 알림 없이 앱을 열어 현재 시각에 직접 체크인한다.
- 하루가 끝날 때 지도와 타임라인으로 이동을 돌아본다.
- 사진, 짧은 메모와 자유 형식 회고로 기억을 보완한다.
- 기록이 쌓이면 주간 비교에서 반복 영역과 새로운 영역을 확인한다.
- 기기를 바꾼 뒤에도 계정으로 기록을 복원한다.

## 6. 핵심 사용자 경험

제품 경험은 세 시간 축으로 이어진다.

1. **매시간 — 기록**: 로컬 알림 또는 수동 진입 → 현재 위치 확인 → 지도 핀과 정확도 반경 확인 → 사용자 확정 → 로컬 저장
2. **매일 — 회고**: 오늘 지도와 시간별 타임라인 → 객관적인 하루 요약 → 선택적인 사진·메모 확인 → 선택적인 하루 회고 작성
3. **매주 — 발견**: 주간 비교 지도 → 반복 영역·새로운 영역·생활 반경 변화에 대한 사실 → 선택적인 회고 질문

놓친 시간은 빈 기록으로 남기며 소급 체크인을 허용하지 않는다. 체크인 위치와 시각은 생성 후 편집할 수 없고 필요하면 체크인 자체를 삭제한다.

## 7. 정보 구조

하단 내비게이션은 다음 세 영역으로 구성한다.

| 영역 | 역할 |

| 오늘 | 현재 체크인 상태, 수동 체크인, 오늘 지도와 타임라인 |
| 캘린더 | 날짜별 체크인과 회고 탐색 |

## 9. 단계별 전달 및 출시 전략

전체 MVP는 하나의 제품 범위로 유지하되 구현과 검증 위험을 네 단계로 나눈다. 각 단계는 이전 단계의 수용 기준을 계속 만족해야 한다.

### M1 — 기록

목표는 자동 추적 없이 빠르고 안정적으로 체크인하고 다시 볼 수 있는지 검증하는 것이다.

M1~M2에서는 로그인 없이 기기 로컬 사용자로 핵심 경험을 사용할 수 있다. M3에서 카카오 로그인이 추가되어도 기존 로컬 기록은 보존되고 사용자가 인증한 FootLog 계정에 중복 없이 연결되어야 한다.

- 활동 시간 설정과 매시간 로컬 알림
- `지금 체크인` 수동 진입
- 현재 위치, 지도 핀과 정확도 반경 표시
- 사용자 확정 후 SQLite 우선 저장
- 오늘 지도와 시간별 타임라인
- 캘린더 날짜별 조회
- 체크인 삭제
- 오프라인 기록과 조회

배포 수준: 프로젝트 소유자와 내부 테스터 대상 내부 테스트.

### M2 — 기억

목표는 위치 기록에 개인적인 맥락을 더하고 하루 회고 경험을 검증하는 것이다.

- 체크인당 사진 1장과 짧은 메모 1개
- 사진 압축과 EXIF 위치정보 제거
- 사진·메모 생성, 수정, 삭제
- 날짜별 자유 형식 회고 본문
- 회고 자동 임시 저장, 완료, 수정, 삭제
- 선택적인 일일 회고 알림
- 지도 핀과 타임라인의 사진·메모 연동

배포 수준: 소수 초대 사용자 대상 비공개 베타 시작.

### M3 — 지속성

목표는 기록을 안전하게 백업하고 기기를 바꿔도 이어서 사용하게 하는 것이다.

- 카카오 소셜 로그인
- 체크인·메모·회고 서버 동기화
- 사진 객체 저장소 백업
- 데이터 종류별 독립적인 실패 처리와 재시도
- 새 기기에서 텍스트 우선 복원, 사진 지연 복원
- 로그아웃 시 로컬 기록 보존과 계정 간 데이터 격리
- 계정 및 서버 데이터 삭제

배포 수준: 비공개 베타 확대 및 동기화 안정성 검증.

필수 기술 선행조건:

- PostgreSQL/PostGIS 운영 DB와 버전 관리되는 마이그레이션
- 사용자, 체크인, 메모, 회고, 사진 메타데이터를 저장하는 서버 데이터 모델
- Spring Boot 인증·동기화·복원·삭제 API
- 사진 객체 저장소
- 클라이언트 UUID 기반 멱등 upsert 계약
- 사용자별 접근 제어와 데이터 격리
- 데이터 종류별 동기화 상태 및 재시도 계약
- 백업·복구와 데이터 보존·삭제 정책

M1부터 UUID와 로컬 데이터 모델을 동기화 가능하게 설계하고, M2에서 사진·메모·회고의 독립 동기화 상태를 정의한다. 서버 기반은 M3 사용자 기능 연결 전에 구축하고 검증한다.

### M4 — 발견

목표는 누적 기록에서 생활 반경과 이동 변화를 객관적으로 발견하게 하는 것이다.

- 주간 비교 지도
- 200m 기준 공간 군집
- 반복 영역과 처음 기록된 영역
- 생활 반경 증감과 요일별 이동 범위
- 첫 주·둘째 주·4주 이상 데이터 단계별 표현
- 정확도 반경 200m 초과 기록의 주간 분석 제외
- 객관적 사실 3~4개와 선택적인 회고 질문

배포 수준: M1~M4 출시 게이트를 모두 통과한 뒤 공개 MVP 출시.

## 10. 기능 요구사항과 수용 기준

### M1 — 기록

#### FR-M1-01 활동 시간과 체크인 알림

사용자는 체크인 알림을 받을 활동 시간대를 설정할 수 있어야 한다.

수용 기준:

- 기기가 설정한 활동 시간 내 매 정시에 로컬 알림을 예약한다.
- 서버는 알림 시각을 결정하거나 푸시하지 않는다.
- 알림 권한을 거부해도 앱과 `지금 체크인`을 사용할 수 있다.
- 활동 시간이나 기기 시간대가 바뀌면 이후 알림을 다시 계산한다.
- 알림을 놓친 시간은 빈 상태로 남고 소급 체크인을 만들지 않는다.

#### FR-M1-02 사용자 확정 체크인

사용자는 현재 위치와 정확도 반경을 확인한 뒤 명시적으로 체크인을 확정할 수 있어야 한다.

수용 기준:

- 위치 확인 중에는 체크인 버튼이 비활성화된다.
- 좌표가 준비되면 지도 핀과 정확도 반경을 표시한다.
- `이 위치에 체크인`을 누르기 전에는 기록을 생성하지 않는다.
- 사용자는 위치를 다시 찾거나 체크인을 취소할 수 있다.
- 핀을 임의로 옮기거나 과거 시각으로 체크인할 수 없다.
- 위치 획득 실패 시 저장하지 않고 재시도 또는 취소를 제공한다.

#### FR-M1-03 로컬 우선 저장

확정된 체크인은 네트워크 상태와 관계없이 기기에 먼저 저장되어야 한다.

수용 기준:

- 네트워크가 없어도 체크인을 완료할 수 있다.
- 앱을 강제 종료하고 다시 실행해도 저장된 기록이 유지된다.
- 로컬 저장에 실패하면 완료로 표시하지 않는다.
- 서버 장애가 체크인 생성과 로컬 조회를 막지 않는다.
- 각 체크인은 기기에서 생성한 고유 UUID를 가진다.

#### FR-M1-04 오늘과 캘린더 조회

사용자는 오늘과 과거 날짜의 체크인을 지도와 시간 순서로 볼 수 있어야 한다.

수용 기준:

- 오늘 화면에 지도 핀과 시간순 타임라인을 표시한다.
- 핀 사이의 선은 실제 경로가 아닌 기록 지점의 시간순 연결임을 표현한다.
- 지도 핀과 타임라인의 선택 상태가 연동된다.
- 캘린더에서 날짜를 선택하면 해당 날짜 기록을 로컬에서 조회한다.
- 체크인이 없는 날은 비난 없는 빈 상태와 날짜 탐색을 제공한다.
- 동일 위치의 여러 체크인을 각각의 시간 기록으로 유지한다.

#### FR-M1-05 체크인 삭제

사용자는 체크인을 확인 후 삭제할 수 있어야 한다.

수용 기준:

- 삭제 전에 연결 데이터가 함께 삭제될 수 있음을 안내한다.
- 삭제 후 오늘, 캘린더와 일일 회고 조회에서 해당 체크인이 사라진다.
- 체크인의 좌표와 시각을 편집하는 기능은 제공하지 않는다.

### M2 — 기억

#### FR-M2-01 사진과 메모

사용자는 체크인 완료를 지연시키지 않고 사진과 메모를 선택적으로 추가할 수 있어야 한다.

수용 기준:

- 체크인당 사진은 최대 1장, 메모는 최대 1개다.
- 체크인 직후 또는 일일 회고에서 생성·수정·삭제할 수 있다.
- 사진 권한을 거부해도 체크인과 메모를 사용할 수 있다.
- 사진은 압축·리사이즈하고 EXIF 위치정보를 제거한 뒤 로컬에 저장한다.
- 사진 처리 실패가 체크인을 삭제하거나 실패 상태로 바꾸지 않는다.
- 체크인 삭제 시 연결된 사진과 메모도 확인 후 삭제한다.

#### FR-M2-02 일일 회고

사용자는 날짜마다 자유 형식 회고 본문 하나를 작성할 수 있어야 한다.

수용 기준:

- 작성 중인 내용을 로컬에 자동 임시 저장한다.
- 사용자가 완료해야 저장된 회고로 처리한다.
- 완료 후에도 수정하거나 삭제할 수 있다.
- 회고 삭제는 체크인 기록에 영향을 주지 않는다.
- 회고를 작성하지 않은 날은 경고나 스트릭 손실 없이 빈 상태로 남는다.
- 이후 체크인이 추가되어도 기존 회고 본문을 자동 변경하지 않는다.

#### FR-M2-03 회고 알림

사용자는 선택한 경우에만 하루 한 번 회고 알림을 받을 수 있어야 한다.

수용 기준:

- 초기 제안 시각은 활동 시간 종료 30분 후다.
- 사용자는 시각을 바꾸거나 알림을 끌 수 있다.
- 해당 날짜에 체크인이 하나 이상 있을 때만 발송한다.
- 알림 전에 회고를 완료했다면 발송하지 않는다.
- 알림에서 진입해도 사용자가 완료하기 전에는 회고 완료로 처리하지 않는다.

### M3 — 지속성

#### FR-M3-01 카카오 로그인과 계정

사용자는 카카오 계정으로 FootLog 계정을 생성하거나 기존 계정에 로그인할 수 있어야 한다.

수용 기준:

- 동일한 카카오 계정으로 로그인하면 동일한 FootLog 계정을 사용한다.
- 서버가 카카오 인증 정보를 검증한 후에만 서버 데이터 접근을 허용한다.
- 인증 실패나 토큰 만료 시 재인증을 요구한다.
- 로그인 실패가 기존 로컬 기록을 삭제하거나 손상하지 않는다.
- 로그인 전에 만든 로컬 기록을 계정에 연결할 때 UUID 기준 중복이 생기지 않는다.
- 로그아웃해도 기기의 로컬 기록을 보존한다.
- 다른 계정의 서버 데이터와 로컬 동기화 데이터가 섞이지 않는다.

#### FR-M3-02 서버 동기화

인증된 사용자의 로컬 기록은 서버에 안전하게 백업되어야 한다.

수용 기준:

- 서버는 클라이언트 UUID를 기준으로 반복 요청을 멱등 처리한다.
- 체크인, 메모, 회고와 사진은 독립적으로 동기화된다.
- 한 데이터 종류의 실패가 다른 종류의 동기화를 막지 않는다.
- 동기화 실패 시 로컬 원본을 보존하고 재시도한다.
- 다른 사용자의 데이터는 조회·수정·삭제할 수 없다.
- 삭제 사항도 재연결 후 서버와 일관되게 동기화된다.

#### FR-M3-03 사진 백업과 새 기기 복원

사용자는 새 기기에서 자신의 기록과 사진을 복원할 수 있어야 한다.

수용 기준:

- 사진 업로드 실패가 텍스트 동기화를 막지 않는다.
- 새 기기에서는 체크인·메모·회고를 먼저 복원한다.
- 사진은 화면에서 필요할 때 내려받는다.
- 반복 복원으로 데이터나 사진 메타데이터가 중복되지 않는다.
- 복원 중 실패한 항목을 재시도할 수 있고 이미 복원된 항목은 유지된다.

#### FR-M3-04 계정과 서버 데이터 삭제

사용자는 계정과 서버에 저장된 개인 데이터를 삭제할 수 있어야 한다.

수용 기준:

- 삭제 대상에 위치·메모·사진·회고와 계정 식별정보가 포함됨을 안내한다.
- 재인증 또는 동등한 본인 확인 후 삭제를 실행한다.
- 삭제 요청의 진행 또는 완료 상태를 사용자에게 알린다.
- 객체 저장소의 사진도 삭제 대상에 포함한다.
- 법적 보존 의무가 없는 삭제 대상은 복원 가능한 사용자 데이터로 남기지 않는다.
- 계정 삭제 완료 후 해당 계정에 연결된 로컬 데이터의 기본값은 기기에서도 삭제하는 것이다. 실행 전에 범위와 복구 불가를 안내한다.
- 삭제한 계정의 로컬 동기화 큐와 인증 정보를 제거하여 재가입 또는 다른 계정 로그인 시 삭제 데이터가 다시 업로드되지 않게 한다.

### M4 — 발견

#### FR-M4-01 데이터 축적 단계별 주간 발견

사용자는 기록 기간에 맞는 주간 이동 사실을 확인할 수 있어야 한다.

수용 기준:

- 첫 주에는 체크인 수, 기록 날짜 수, 기록 영역과 가장 넓게 이동한 날을 표시한다.
- 둘째 주부터 지난주와 겹치는 영역, 처음 기록된 영역, 생활 반경 증감과 요일별 이동 범위를 표시한다.
- 4주 이상이면 최근 4주 개인 기준선, 평소 영역, 드문 영역과 생활 반경 추세를 표시한다.
- 데이터가 부족하면 비교를 만들지 않고 언제 가능해지는지 안내한다.

#### FR-M4-02 공간 비교 규칙

주간 발견은 일관되고 설명 가능한 공간 규칙을 사용해야 한다.

수용 기준:

- 서로 200m 이내인 체크인 지점을 하나의 영역으로 묶는다.
- 새로운 영역은 비교 기간 이전 기록에 같은 군집이 없는 영역으로 정의한다.
- 정확도 반경이 200m를 초과한 체크인은 주간 영역 비교에서 제외한다.
- 분석에서 제외된 체크인도 일일 기록에는 그대로 표시한다.
- 200m 기준 변경은 출시 후 정확도 분포와 사용자 피드백을 근거로 별도 제품 결정으로 승인한다.

#### FR-M4-03 비평가적 발견 표현

주간 발견은 사용자를 평가하지 않고 사실과 선택적인 질문만 제공해야 한다.

수용 기준:

- 점수, 순위, 스트릭과 성취 배지를 사용하지 않는다.
- 반복되는 생활을 부정적으로 표현하지 않는다.
- 새로운 장소 방문을 직접 지시하지 않는다.
- 핵심 사실은 한 화면에 3~4개로 제한한다.
- 회고 질문은 선택 사항이며 응답하지 않아도 불이익이 없다.

## 12. 성공 지표

### 핵심 성공 지표

**주간 공간 회고 사용자 비율**

한 주에 3일 이상 체크인하고, 해당 주에 일일 회고 화면을 1회 이상 확인한 활성 사용자의 비율이다.

- 한 주는 사용자의 현재 기기 시간대를 기준으로 월요일 00:00부터 다음 월요일 00:00 직전까지다.
- 활성 사용자는 해당 주에 앱을 한 번 이상 실행한 고유 사용자다.
- 분자는 활성 사용자 중 서로 다른 3일 이상에 체크인을 하나 이상 남기고, 같은 주에 일일 회고 화면을 한 번 이상 연 사용자다.
- `주간 유지 사용자`는 첫 체크인 이후 다음 관측 주에도 앱을 한 번 이상 실행한 사용자다.
- 이 지표 이름의 `공간 회고`는 일일 지도 회고 행동을 뜻하며 M4 `발견` 화면 열람을 뜻하지 않는다.

### 공개 MVP 초기 가설

| 지표 | 초기 목표 |
|---|---:|
| 가입 후 24시간 내 첫 체크인 완료율 | 70% 이상 |
| 주간 공간 회고 사용자 비율 | 40% 이상 |
| 첫 체크인 사용자 기준 4주차 유지율 | 25% 이상 |
| 주간 유지 사용자 중 주 3일 이상 체크인 비율 | 50% 이상 |
| 체크인이 있는 날의 일일 회고 화면 열람률 | 35% 이상 |

초기 목표는 공개 MVP의 즉시 합격·실패를 판정하는 절대 기준이 아니라 출시 후 첫 4주 동안 검증할 제품 가설이다. 표본 수와 관측 기간을 함께 보고 조정한다. 사진·메모 작성률은 핵심 가치가 아닌 기능 활용 보조 지표로 사용한다.

제품 분석은 위치 원본이나 회고 본문을 불필요하게 수집하지 않는 방식으로 설계한다. 지표 이벤트와 개인정보 항목은 구현 전에 별도 분석·개인정보 명세에서 승인한다.

## 13. 단계별 출시 게이트

### M1 내부 테스트 진입

- 사용자 확정 전 위치 기록이 생성되지 않는다.
- 오프라인 체크인과 앱 재실행 후 조회가 가능하다.
- 오늘 지도, 타임라인과 캘린더가 동작한다.
- 백그라운드 위치 권한이나 수집 API를 사용하지 않는다.
- M1 핵심 사용자 경로와 회귀 테스트가 통과한다.

### M2 비공개 베타 시작

- M1 출시 게이트를 계속 통과한다.
- 사진·메모·회고의 생성·수정·삭제가 동작한다.
- 사진 EXIF 위치정보 제거가 검증된다.
- 사진 실패가 체크인을 손상하지 않는다.
- 회고 알림의 발송·억제 조건이 검증된다.

### M3 비공개 베타 확대

- M1~M2 출시 게이트를 계속 통과한다.
- 카카오 로그인과 사용자별 데이터 격리가 검증된다.
- PostgreSQL/PostGIS 스키마와 마이그레이션이 재현 가능하다.
- 인증·동기화·복원·삭제 API가 통합 테스트를 통과한다.
- 객체 저장소 백업과 복원이 검증된다.
- UUID 멱등성과 오프라인 재시도가 검증된다.
- 새 기기 복원 시 데이터 유실과 중복이 없다.

### M4 공개 MVP 출시

- M1~M3 출시 게이트에 회귀가 없다.
- 첫 주·둘째 주·4주 이상 발견 상태가 검증된다.
- 200m 공간 군집과 저정확도 제외 규칙이 검증된다.
- 반복 생활을 평가하거나 압박하는 표현이 없다.
- 온보딩부터 체크인, 일일 회고, 동기화·복원과 주간 발견까지 핵심 사용자 여정이 통과한다.
- 개인정보 처리, 계정 삭제와 앱스토어·플레이스토어 출시 체크리스트가 완료된다.
- 16절의 미결정 사항 중 해당 단계의 구현·검증에 필요한 설계가 승인되고 수용 테스트에 반영된다.

## 14. 기술 경계와 별도 설계 문서

PRD는 제품 동작과 완료 조건을 정의한다. 다음 구현 상세는 PRD 요구사항을 근거로 별도 문서에서 결정한다.

- DB 엔터티, 필드, 관계, 인덱스, 보존과 마이그레이션 전략
- API 경로, HTTP 메서드, 요청·응답 스키마, 오류 코드와 버전 정책
- 카카오 OAuth 흐름, 토큰 저장·갱신과 서버 검증 방식
- 동기화 충돌, 삭제 전파, 재시도와 백오프 프로토콜
- 객체 저장소 제공자, 업로드 방식과 이미지 파생본 정책
- 주간 발견 공간 계산의 구체적인 알고리즘과 성능 전략
- 제품 분석 이벤트와 개인정보 최소 수집 정책

기술 설계는 다음 불변 조건을 지켜야 한다.

- 체크인은 항상 로컬에 먼저 저장한다.
- 서버 upsert 키는 클라이언트 UUID다.
- 알림은 기기가 전담한다.
- 백그라운드 상시 위치 권한을 요구하지 않는다.
- 위치·메모·사진·회고의 동기화 실패를 서로 격리한다.

## 15. 위험 요소와 대응

| 위험 | 영향 | 제품 대응 |
|---|---|---|
| 매시간 체크인의 피로도 | 알림 해제와 이탈 | 활동 시간 설정, 수동 체크인 유지, 놓친 시간에 대한 압박 금지 |
| 낮은 GPS 정확도 | 잘못된 기록과 발견 | 정확도 반경 표시, 다시 찾기, 200m 초과 기록의 주간 분석 제외 |
| 동기화 복잡성 | 중복·유실·계정 간 혼합 | 로컬 원본 보존, UUID 멱등성, 데이터 종류별 상태, 사용자 격리 테스트 |
| 사진 저장 비용과 실패 | 비용 증가와 체크인 지연 | 1장 제한, 압축·리사이즈, 지연 복원, 텍스트와 업로드 분리 |
| 데이터 부족 | 무의미한 주간 발견 | 축적 기간별 표현, 부족 상태 안내, 억지 비교 금지 |
| 민감한 위치 데이터 노출 | 사용자 신뢰와 안전 훼손 | 최소 권한, 백그라운드 수집 금지, 접근 제어, EXIF 제거, 삭제 기능 |
| 기능 범위 과대 | 공개 출시 지연 | M1~M4 단계별 검증과 배포, 각 단계의 출시 게이트 운영 |

## 16. 미결정 사항 관리

다음 항목은 현재 PRD의 제품 방향을 막지 않지만 관련 단계 착수 전에 별도 결정이 필요하다.

| 항목 | 결정 시점 | 결정 산출물 |
|---|---|---|
| 카카오 인증과 FootLog 계정 식별·탈퇴 세부 정책 | M3 구현 전 | 인증·계정 설계 |
| DB 스키마와 API 계약 | M3 기반 구축 전 | DB 설계서, OpenAPI 명세 |
| 동기화 충돌 및 삭제 전파 정책 | M3 구현 전 | 동기화 프로토콜 설계 |
| 객체 저장소와 이미지 규격 | M2 사진 구현 전 | 사진 저장·백업 설계 |
| 성능 예산과 측정 환경 | 각 단계 배포 전 | 성능 명세와 측정 결과 |
| 분석 이벤트와 동의·보존 정책 | 비공개 베타 전 | 분석·개인정보 명세 |
| 주간 경계, 군집 연결 규칙과 생활 반경 계산식 | M4 구현 전 | 주간 발견 알고리즘 명세 |
| 온보딩 완료 조건과 스토어 출시 증빙 | 각 배포 단계 전 | 배포·출시 체크리스트 |

미결정 사항은 임의의 구현 선택으로 제품 동작을 고정하지 않는다. 결정이 사용자 경험, 범위 또는 수용 기준을 바꾸면 이 PRD를 먼저 갱신한다.
