# FootLog 알림 설정 화면 개선 설계

- 작성일: 2026-08-19
- 상태: 승인됨
- 관계: `2026-08-02-location-checkin-diary-design.md`의 "알림 주기: 고정 1시간 단위" 핵심 설계 결정을 유지한 채, `mobile/src/features/notifications/NotificationSettingsScreen.tsx`(매시간 체크인 알림 설정 화면)의 UX만 개선한다. 회고 알림(`2026-08-06-core-ux-flow-design.md` 6장, PRD FR-M2-03)은 아직 구현되지 않은 기능이라 이 문서 범위 밖이다.

## 1. 배경과 범위

현재 알림 설정 화면은 활동 시간대(시작/종료 시각)를 24개 시간 버튼을 가로 스크롤하며 하나씩 골라야 하고, 스위치는 조작 즉시 반영되지만 시간대 변경은 별도 "저장" 버튼을 눌러야 반영되는 등 조작 방식이 일관되지 않다. 또한 활동 시간대 전체(예: 07~23시)마다 매시간 알림이 오는 구조라 사용자가 부담을 느낄 수 있는데, 이를 완화할 장치가 없다.

이 문서는 조작 편의성 개선을 최우선으로 하고, 그 다음으로 알림 피로도를 낮추는 장치(알림 간격 조정)를 다룬다. 우선순위는 다음과 같다.

1. 활동 시간대 설정의 조작 편의성 (프리셋 + 슬라이더)
2. 알림 피로도 관리 (알림 간격 조정)
3. 화면 전체 상호작용 구조 재설계 (즉시 적용, 저장 버튼 제거)
4. 현재 상태를 한눈에 보여주는 정보 표시 (하루 알림 횟수)

### 포함

- 활동 시간대 선택 UI를 프리셋 칩 + 듀얼 핸들 레인지 슬라이더 조합으로 교체
- 알림 간격 선택(1시간 / 2시간 / 3시간) 추가
- 모든 설정 변경이 즉시 적용되는 상호작용 모델로 전환 (저장 버튼 제거)
- "하루 N회 알림" 실시간 요약 표시
- `NotificationSettings`에 `intervalHours` 필드 추가 및 기존 데이터 하위 호환

### 제외

- 회고 알림(별도 시각 설정, 온/오프) — 아직 구현되지 않은 기능이라 이번 화면에 포함하지 않는다. 향후 회고 알림이 추가될 때는 별도 설계 문서에서 이 화면과의 배치 관계(같은 화면 내 별도 섹션 vs 별도 화면)를 다시 정한다.
- 자정을 넘기는 활동 시간대(예: 22시~새벽 2시) 지원 — 데이터 검증(`startHour < endHour`)과 스케줄러가 자정 교차를 다루지 않는다. 이 제약을 없애려면 검증 로직과 알림 계산 로직 전반을 다시 설계해야 하므로 별도 작업으로 분리한다.
- "오늘 하루 스누즈", "요일별 알림 제외" 등 다른 피로도 완화 기능 — 이번 슬라이스는 알림 간격 조정만 다룬다.
- 회고 화면(`buildTimelineHours`)의 1시간 격자 변경 — 알림 간격은 알림 발송 시점에만 영향을 주고, 일일 회고 타임라인의 기록 단위(1시간)는 그대로 유지한다.

## 2. 왜 회고 타임라인의 1시간 격자는 그대로 두는가

`DailyDetailScreen.tsx`의 `buildTimelineHours`는 활동 시간대 안의 모든 정수 시간을 슬롯으로 만들고, 체크인이 있으면 채우고 없으면 빈 슬롯으로 표시한다. 이 1시간 격자는 다음을 지탱한다.

- 날짜 간 비교 가능성(매일 같은 격자라야 "이 시간대는 항상 비어있다" 같은 패턴을 읽을 수 있음)
- "빈 슬롯 = 기록 없음"이라는 일관된 의미(알림 간격에 따라 빈 슬롯의 의미가 달라지면 회고 시 혼란을 준다)
- 하루 요약의 연속 체크인 영역 계산 등 통계 로직의 단순성

따라서 알림 간격 조정은 **"언제 알림을 보낼지"만 바꾸고, "기록을 몇 시 단위로 보여줄지"는 바꾸지 않는다.** 알림이 없는 시간에도 사용자는 "지금 체크인"으로 자유롭게 기록할 수 있고, 그 기록은 지금처럼 해당 정수 시간 슬롯에 들어간다.

## 3. 데이터 모델

`mobile/src/features/settings/AppSettingsRepository.ts`의 `NotificationSettings`에 `intervalHours` 필드를 추가한다.

```ts
export type NotificationSettings = {
  enabled: boolean;
  startHour: number;
  endHour: number;
  intervalHours: number;   // 신규: 1 | 2 | 3
  scheduledIds: string[];
};
```

- 허용 값은 1, 2, 3이다. `decodeNotificationSettings`의 검증에 `intervalHours`가 이 세 값 중 하나인지 확인하는 조건을 추가한다.
- 기존에 저장된 설정(마이그레이션 이전 데이터)에는 이 필드가 없다. 디코딩 시 `intervalHours`가 없거나 유효하지 않으면 `1`로 간주해 하위 호환을 유지한다 — 별도 DB 마이그레이션 없이 애플리케이션 레벨 기본값 처리로 충분하다.
- `DEFAULT_NOTIFICATION_SETTINGS`에도 `intervalHours: 1`을 추가한다.

## 4. 알림 스케줄 계산

`ExpoNotificationScheduler`가 활동 시간대와 간격을 받아 알림 시각 목록을 계산하는 방식을 다음과 같이 정의한다.

- 시작 시각부터 간격만큼 더해가며, 종료 시각을 넘지 않는 시각까지 알림을 예약한다.
- 예: 시작 07시, 종료 22시, 간격 2시간 → 07, 09, 11, 13, 15, 17, 19, 21시 (8회). 22시는 간격에 맞지 않으므로 알림이 없다.
- 간격 1시간(기본값)일 때는 기존 동작과 동일하게 매 정시 알림이 온다.
- "하루 N회 알림" 요약 문구는 이 계산식으로 나온 알림 개수를 그대로 보여준다.

## 5. 화면 구조와 상호작용

화면 구성 순서(위→아래):

1. 제목("체크인 알림") + 설명 문구
2. 체크인 알림 ON/OFF 스위치
3. 활동 시간대 — 프리셋 칩(출근형 07–22, 자유형 09–23, 아침형 05–20) + 듀얼 핸들 레인지 슬라이더
4. 알림 간격 — 세그먼트 버튼(1시간 / 2시간 / 3시간)
5. "하루 N회 알림" 요약(3, 4 변경 시 실시간 갱신)
6. 오류/안내 메시지 (권한 거부 등, 기존 로직 유지)

**상호작용 원칙: 모든 조작은 즉시 반영된다.** 스위치, 프리셋 칩, 슬라이더 드래그, 간격 버튼 중 무엇을 조작해도 그 즉시 `scheduler.reschedule()`이 호출되어 알림이 재예약되고 저장소에 반영된다. 화면 하단의 별도 "저장" 버튼은 제거한다 — 지금처럼 "스위치는 즉시 반영되는데 시간 변경은 저장을 눌러야 하는" 불일치를 없애기 위함이다.

- 프리셋 칩을 탭하면 슬라이더가 해당 구간으로 즉시 이동하고 그 값이 바로 적용된다.
- 슬라이더를 직접 끌면 어떤 프리셋 칩도 선택되지 않은 상태가 되고("직접 설정"은 탭 가능한 칩이 아니라, 현재 구간이 어떤 프리셋과도 일치하지 않을 때 표시되는 상태 라벨이다), 끌기를 마친 값이 바로 적용된다.
- 알림 권한이 꺼져 있어 예약이 실패하면, 기존 `syncAfterFailure`와 동일하게 이전 상태로 되돌리고 안내 메시지를 보여준다.
- 잦은 드래그로 인한 과도한 재스케줄링 호출을 막기 위해, 슬라이더 조작은 드래그가 끝난 시점(release)에 한 번만 `reschedule()`을 호출한다. 프리셋 칩과 간격 버튼은 탭 즉시 호출한다.

## 6. 프리셋의 자정 교차 제약

프리셋 시간대는 모두 `startHour < endHour`를 만족하는 당일 내 구간으로 제한한다. 자정을 넘기는 생활 패턴(예: 야간 근무자의 22시~새벽 2시)은 이번 설계에서 지원하지 않는다 — 지원하려면 `AppSettingsRepository`의 검증 로직과 `ExpoNotificationScheduler`의 스케줄 계산이 자정 교차를 다루도록 다시 설계해야 하고, 이는 이번 화면 개선의 범위를 넘어선다.

## 7. 테스트 관점

- `decodeNotificationSettings`: `intervalHours`가 없는 기존 저장값을 1로 해석하는지, 1/2/3 외 값은 거부하는지
- 알림 스케줄 계산: 시작/종료/간격 조합별 알림 횟수와 시각이 기대대로 나오는지(경계값 포함 — 간격이 구간 길이를 나누어떨어지지 않는 경우)
- 프리셋 선택 → 슬라이더 값 반영 → 즉시 재스케줄 호출까지의 흐름
- 슬라이더 드래그 중에는 재스케줄이 호출되지 않고, 드래그 종료 시 한 번만 호출되는지
- 권한 거부 시 롤백 동작(기존 `syncAfterFailure` 경로)이 새 상호작용 모델에서도 동일하게 동작하는지
