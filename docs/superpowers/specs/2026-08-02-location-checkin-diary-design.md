# 위치 체크인 다이어리 앱 — 설계 문서

- 작성일: 2026-08-02
- 상태: 승인됨 (구현 계획 수립 대기)

## 배경 및 목적

매일 시간 단위로 현재 위치를 기록해, 텍스트 일기가 감정/사건을 회고하듯 **공간적으로 자신의 삶을 회고**할 수 있는 앱. 자주 가는 곳과 새로운 곳을 구분해 인식하게 함으로써, 반복되는 동선에서 벗어나 더 다양한 장소를 방문하도록 동기를 부여하는 것이 궁극적 목표. MVP는 "기록 + 회고"까지만 다루고, 장소 방문 패턴 분석/시각화는 v2로 분리한다.

## 핵심 설계 결정

| 항목 | 결정 |
|---|---|
| 플랫폼 | React Native (iOS + Android 동시 대응) |
| 알림 주기 | 고정 1시간 단위 |
| 알림 시간대 | 사용자가 설정한 "활동 시간대" 내에서만 (수면 시간대 알림 없음) |
| 미응답 처리 | 해당 시간대는 빈 자리로 남김 (소급 캡처 없음) |
| 캡처 방식 | 알림 + 능동 위치 체크인 (SetLog의 "알림+능동 캡처" 패턴 차용, 단 순수 로컬 방식) |
| 위치 권한 | "앱 사용 중"(When In Use)만 요구 — 백그라운드 상시 추적 없음 |
| 데이터 저장 | 로컬(SQLite) 우선 저장 + 서버 백업/동기화 |
| 백엔드 | Spring Boot |
| 데이터베이스 | PostgreSQL + PostGIS |
| 인증 | Apple / Google 소셜 로그인만 (이메일/비밀번호 없음) |
| 장소 표시 | 좌표/지도 핀만 (역지오코딩 없음, v2로 이연) |
| MVP 범위 | 체크인 기록, 캘린더로 과거 로그 다시보기, 하루 단위 자동 요약(지도 핀 모음) |
| v2 후보 | 자주 가는 곳 vs 새로운 곳 분석/시각화, 역지오코딩 기반 장소명 표시 |

### 알림 구현 방식에 대한 근거

SetLog는 그룹 멤버 전원이 정확히 동시에 알림을 받아야 하는(강제 동시성) 요구사항 때문에 서버 푸시 기반으로 알림을 구현했을 것으로 추정된다. 반면 본 앱은 개인 회고용으로 그룹 동기화 요구사항이 없으므로, 기기 로컬 알림(각 기기가 자체적으로 활동 시간대에 맞춰 알림을 예약)이 더 적합하다. 이 방식은 서버가 알림 타이밍을 몰라도 되어 서버 복잡도를 낮추고, 오프라인에서도 100% 동작하며, iOS의 까다로운 "Always" 위치 권한 심사를 피할 수 있다는 장점이 있다.

## 아키텍처

```
[React Native App]                         [Spring Boot Backend]
 ├─ NotificationScheduler                    ├─ AuthController
 │   (기기 로컬 알림 예약, iOS/Android)         │   (Apple/Google 토큰 검증 → JWT)
 ├─ CheckInScreen                            ├─ EntryController
 │   (알림 탭 → GPS 위치 체크인)                │   (위치 기록 upsert/조회, idempotent)
 ├─ LocalStore (SQLite)                      ├─ UserSettingsController
 │   (오프라인 우선 저장)                       │   (활동 시간대 설정 동기화)
 ├─ SyncService                     <--HTTP-->│
 │   (온라인 시 백그라운드 동기화)               │
 ├─ CalendarView / DailySummaryView           └─ PostgreSQL + PostGIS
 └─ (온보딩: 소셜로그인, 위치권한,
     알림권한, 활동시간대 설정)
```

핵심 원칙은 **로컬 우선(local-first)**: 체크인은 항상 로컬 SQLite에 먼저 저장되고, 서버는 백업과 다기기 동기화 역할만 담당한다.

## 주요 컴포넌트

### 모바일 (React Native)

| 컴포넌트 | 역할 |
|---|---|
| `NotificationScheduler` | 매일 활동 시간대 내 매시간 로컬 알림을 예약. 앱 실행/자정마다 다음 24시간치 재계산 |
| `CheckInScreen` | 알림 탭 시 진입, `getCurrentLocation()`으로 현재 위치를 즉시 획득해 로컬 저장 |
| `LocalStore` (SQLite) | `check_ins` 테이블: 오프라인 우선 기록 저장소 |
| `SyncService` | 앱 포그라운드 진입/네트워크 복구 시, 미동기화 항목을 서버로 push (백그라운드 태스크) |
| `CalendarView` | 날짜별 과거 로그 탐색 (로컬 우선 조회) |
| `DailySummaryView` | 하루치 체크인들을 지도 핀으로 모아 보여주는 자동 요약 화면 |
| `OnboardingFlow` | 소셜 로그인 → 위치/알림 권한 요청 → 활동 시간대 설정 |

### 백엔드 (Spring Boot)

| 컴포넌트 | 역할 |
|---|---|
| `AuthController` | Apple/Google idToken 검증 → 자체 JWT 발급 |
| `EntryController` | 위치 기록 upsert(클라이언트 UUID 기반, idempotent) / 조회 API |
| `UserSettingsController` | 활동 시간대 등 설정값 서버 동기화 (다기기 대비) |
| `User`, `LocationEntry` (PostGIS) | DB 스키마 |

## 데이터 흐름

1. **최초 설정**: 소셜 로그인 → 위치 권한("사용 중")·알림 권한 요청 → 활동 시간대 설정(예: 07:00~23:00)
2. **알림 예약**: `NotificationScheduler`가 활동 시간대 내 매 정시 로컬 알림을 다음 날치까지 미리 예약
3. **체크인**: 알림 탭 → `CheckInScreen`이 현재 위경도+타임스탬프를 즉시 GPS로 획득 → `LocalStore`에 저장 (status: `unsynced`)
4. **동기화**: `SyncService`가 앱이 포그라운드로 오거나 네트워크가 살아날 때 미동기화 항목을 서버에 배치 전송 → 서버는 클라이언트 UUID 기준 upsert
5. **다시보기**: `CalendarView`는 기본적으로 로컬 DB에서 읽음(오프라인 동작) — 새 기기에서 로그인 시엔 서버에서 과거 기록을 내려받아 로컬에 채움
6. **하루 요약**: 그날 체크인된 항목들을 `DailySummaryView`에서 지도 핀으로 표시 (자정 지나면 자동으로 "완료된 하루"로 캘린더에 편입)

## 에러 처리

| 상황 | 처리 방식 |
|---|---|
| 위치 권한 거부 | `CheckInScreen`에 "위치 권한이 필요합니다" 안내 + 설정 앱 딥링크. 해당 시간대는 빈 자리로 남음 |
| GPS 획득 실패/타임아웃 | 1회 재시도 → 그래도 실패하면 실패로 표시, 캘린더에 "실패" 아이콘 정도로만 부드럽게 노출 |
| 알림 권한 거부 (온보딩 시) | 앱은 계속 사용 가능. 홈 화면에 "지금 체크인" 버튼으로 수동 기록 가능, 알림 켜기는 권장만 |
| 동기화 실패 (네트워크/서버 오류) | 로컬 저장은 이미 끝난 상태라 데이터 유실 없음. `unsynced` 큐에 남아 지수 백오프로 재시도 |
| 소셜 로그인 토큰 만료 | 재로그인 유도. 로컬 데이터는 로그인 여부와 무관하게 보존됨 |
| 기기 시간대/시계 변경 | 매일 재계산되는 스케줄러 덕분에 다음날부터 자동 반영 (당일 오차는 허용) |
| 서버 재동기화 시 중복 저장 | 클라이언트 UUID를 PK로 upsert하므로 재전송해도 중복 안 생김 |

## 테스트 전략

**모바일**
- 단위 테스트: 활동 시간대 → 알림 시각 계산 로직 (경계값, 자정 걸침, 서머타임/타임존 변경 케이스)
- 통합 테스트: 위치 모킹 → `CheckInScreen` 체크인 → 로컬 DB 저장 검증
- 동기화 테스트: 오프라인 큐 적재, 재시도/백오프, 서버 upsert 멱등성 검증

**백엔드 (Spring Boot)**
- Testcontainers로 실제 PostgreSQL/PostGIS 띄워 통합 테스트
- 인증: Apple/Google 토큰 검증 로직, 만료/위조 토큰 케이스
- Entry API: upsert 멱등성, 사용자별 데이터 격리(다른 유저 데이터 조회 안 되는지) 검증

**E2E**
- 핵심 경로 (온보딩 → 권한 승인 → 알림 → 체크인 → 캘린더 확인) 는 Detox 등으로 자동화하거나 최소한 수동 QA 체크리스트로 커버

## 범위 밖 (v2 후보)

- 자주 가는 곳 vs 새로운 곳 분석/시각화 (히트맵, 방문 지수 등)
- 역지오코딩 기반 장소명 표시
- 다기기 동시 사용을 위한 설정 실시간 동기화 고도화
- 그룹/소셜 공유 기능
